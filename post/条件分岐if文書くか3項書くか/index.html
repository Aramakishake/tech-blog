はじめに

お仕事や趣味でC言語やC#でプログラムを書く傍ら、沸々と疑問が湧いてきている。

「2択の条件分岐を使うとき、書き方がいくつかあるが、どれが良いんだろうか？」

これについて考えが浮かんでは消えゆくのを繰り返していたが、一旦整理してみようと思い、今回筆を執った。

結論を急ぐ諸兄が取るべき行動を、3項演算子を使って表す。

行動 = 結論を急ぐ ? おわりにを読む : 次から読む

前提

まず、考え易いようにどのような設定で考えるかを明確にしよう。

bool型のconditionが

  • trueのとき、valueにはAを詰める
  • falseのとき、valueにはBを詰める

という前提でどういう書き方がいいのだろうか？

というもの。とりあえずC言語で書く。

以下にどのような択があるかについて提示する。

提示したもの以外にもありそうだが、まぁパッと思いつくものとして4つ挙げる。

ただ、パッと出てきた段階で「できるけど流石にこれはないだろ～」と思ったのは、穴とか大穴にした。

理由に関しては判断基準についての提示の項で後述する。

候補群の紹介

本命 if文

if(condition)
{
    // trueの処理
    value = A;
}
else
{
    // falseの処理
    value = B;
}

conditionがtrueの場合valueにはAが、 conditionがfalseの場合valueにはBが代入される

利点

  • This is 分岐という書き方なので、意図は伝わりやすそう。

欠点

  • 1つの分岐に掛ける行数が多い。

対抗 3項演算子

value = condition ? A : B;

利点

  • すっきりと1行で書ける。

欠点

  • 慣れてないとどっちがtrueのときの値だっけ？となる。
  • 読んでる途中でvalueにconditionを入れる…と思ったら3項演算子か～ってなって1行の間にする。

穴 switch文

switch(condition)
{
    case true:
        // trueの処理
        value = A;
        break;
    case false:
        // falseの処理
        value = B;
        break;
    default:
}

利点

  • 2択から択が増えたとき対応可能。

欠点

  • 今は2択なので冗長すぎる。
  • 3択が必要になったらbool型もenumとかになるだろうし、無駄。

大穴 論理積

condition && value = A;
condition || value = B;

論理積をとるとき、左側を先に評価する(短絡評価)。

condition = trueのとき

これはどういうことかというと、 condition = true の場合、1行目の左側はtrueであり、まだ condition && value = A; の真理値は確定しない。

そのため、value = Aを実行して評価するため、valueにはAが代入される。

次に2行目に関しては、condition = trueの場合、 condition || value = B;の真理値は確定してしまう。

そのため、value = Bは実行されず、評価されない。

つまるところ、valueに関してはAのみが代入されることになる。

condition = falseのとき

今度は1行目のときに、condition && value = A; の真理値はfalseで確定してしまうので、これ以上計算は不要となる。

そのため右側は実行されず、評価もされない。

一方で、2行目のときには、左側がfalseのときには、condition || value = Bの真理値は確定しない。

そのため、value = Bは実行され、評価される。

以上により、valueに関してはBのみが代入されることになる。

利点

  • オシャレ

欠点

  • あまりにもオシャレ過ぎて、意図が伝わりにくい
  • ふざけんな、プログラミングはオナニーの道具じゃねぇ

判断基準

まず、プログラミングする上で複数の選択肢がある場合、どういう基準で選択するかを明示する。

伝わり易くしよう

修正する人(他人や数年後の自分)にも 「ここはこういう意図で書いたよ」 という旨が伝わるような書き方にすべきだと考えている。

一人で開発するとしても、過去の自分の判断を100%覚えているなんてことは無いだろうから、伝わり易くするに越したことはないと考えている。

ここから、論理積の手法は無いだろ～と判断した。

今使わんものは、今作らんでもいい

すぐ使う必要のないものを、「一応あとで使うかもしれないし、作っておこう」というのは、避けるべしという考え。

理由としては、現在不要なもののために、わざわざコードを複雑化させる意味はないため。

YAGNI原則(You Ain’t Gonna Need It)として言われてるらしい。

ここから、2択の分岐をswitch文で書く手法は無いだろ～と判断した。

逡巡の過程

まず、結論としては、3項演算子を使ってみようというものであるが、if文とどっちが良いのか？という逡巡の過程を書く。

今回の争点

まず、先述の「伝わり易くしよう」というのが判断する上でのキーポイントとして考えている。

が、「誰に？」と「何を？」という点については考慮の余地がある。 極端なことをいえば、3項演算子しか知らない人間に条件分岐で値が変わる旨を伝えたいならば、3項演算子で書く他ない。 その中でどう判断するべきか、ということを考えていきたい。

「誰に？」

この記事を書いてる今の私は分かるが、過去の私は分かっていなかった。

自分よりも年上のC言語ソースコードを修正してきたという経緯もあるかもしれないが、 私の認識としては、if文はプログラミング基本構文に含まれるが、3項演算子は含まれないという認識である。

ということを考えると「誰にでも伝わる」と思われる、if文がわずかにリード。

「何を？」

これは処理の構造だと考えている。今回だと「分岐する」ということである。

if文だったら、ネストすればするほどどの分岐かわかり辛くなる。 3項演算子だったら、意味を了解できていればわかり易くなる。

誰にでも伝わるif文 vs. 構造を単純化する3項演算子

ということで、

  • 伝わりやすさの点では、if文
  • 構造の伝えやすさの点では、3項演算子

がそれぞれ勝利を収めた。

ただ、3項演算子の学習コストなんて大したことはない(true/falseの順序くらい？)ように思える。

よく考えてみると、Excelとかのif文の順序も=if(condition, value_if_true, value_if_false)だったりするので、 慣れろ！！！ と思うのであった。

また、こうやって成長するにつれて、ｴﾝｼﾞﾆｬｰは新人に厳しい人間になっていくんだなと思うのであった。

結論：3項演算子でええやん

ということで、ここからは3項演算子のウィニングランである。

とはいえ、構文わかりにくくないか？？

構文を読んでるときの気持ち

A = B ? C : D

という表現があったときの思考の流れを示す。

  1. AにB代入するんだな～
  2. …って思ったら3項演算子やんけ！？
  3. えぇと…Bという条件を満たすならCだっけDだっけ…？確か…C？
  4. 意味合いそうだ、一応調べとくか
  5. あぁやっぱCがtrueの場合でDがfalseの場合だよな

という流れになる。流石に最近慣れてきたので、最近は3.で終了するようになったが…。 っていうか、Aの型がintとかfloatだったらそもそも1にならんかも…。

ただし、Aの型もboolだったらやっぱり混乱しそうではある。 ということで次の例を挙げる。

3項演算子、やっぱりムズいやつはムズい

if (value == null ? this.value2 != null : !value.Equals(this.value2))
  • こり、if文の中に3項演算子(つまり分岐)が入ってて、1項目はもちろん条件文なんですけど
  • 2項目と3項目も条件文なんで、条件文の結果出てくるものが条件文というムズさがある
  • valueがnullかどうかで分岐
    • nullのとき、value2がnullかどうかのbool値
    • nullでないとき、valueとvalue2が一致するかのbool値

3項演算子でミスったこと : break挟めんやん

3項演算子慣れかけのタイミングでミスった例を示す。

やりたいこと

for(int ii; i < ii_max; ii++)
{
    if(condition)
    {
        value = func(ii);
        break;
    }
    else
    {
        value = func2(ii);
    }
}

conditionがtrueのときだけループを抜けたい、という処理。

実際やっちゃったこと

for(int ii; i < ii_max; ii++)
{
    value = condition ? func(ii) : func2(ii);
    break;
}

こっちはtrue気分でbreakを書いちゃった間違ってる処理。 1回valueに代入しただけで抜けちゃうお茶目処理だ。

まぁ、振り返るとアホなミス。

おわりに

3項演算子とif文は似て非なるものではあるが、どちらでも書けるというときは3項演算子で書こうという結論に至った。
